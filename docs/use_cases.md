# Use Cases: nutrition_agent

Документ описывает сценарии использования Python-пакета `nutrition_agent` — агентского движка для анализа и записи данных о питании.

Пакет не зависит от интерфейса (Telegram, веб, CLI). Use Cases описывают **входы и выходы** публичного API, а не кнопки в UI.

---

## Условные обозначения

- **Актор** — тот, кто вызывает пакет (обёртка бота, веб-сервер, CLI).
- **Sink** — модуль записи (Google Fit, Local SQLite, Fitatu и т.д.).
- **ProcessResult** — объект, который возвращает `agent.process(...)`.

---

## UC-01: Запись приёма пищи через текст (базовый)

**Актор:** Разработчик (обёртка бота/приложения).

**Предусловие:** Пакет сконфигурирован с хотя бы одним Sink (например, `LocalSQLiteSink`).

**Основной поток:**

1. Обёртка вызывает `agent.process(text="Съел две котлеты и гречку 200г")`.
2. Пакет отправляет текст в LLM с промптом для извлечения структуры.
3. LLM возвращает JSON, валидируемый Pydantic-моделью `NutritionEntry`.
4. Пакет последовательно вызывает `write()` у всех активных Sink-ов.
5. Пакет возвращает обёртке `ProcessResult` (успех/ошибка, записанные данные, список сработавших Sink-ов).

**Постусловие:** Запись появилась в локальной БД (или Google Fit).

**Исключения:** LLM вернул невалидный JSON → пакет возвращает `ProcessResult(status="error", reason="parse_failed")` с сырым ответом для отладки.

## UC-02: Запись через голосовое сообщение

**Актор:** Разработчик.

**Основной поток:**

1. Обёртка скачивает `.ogg` файл из Telegram и передаёт `agent.process(audio_bytes=...)`.
2. Пакет вызывает внутренний `transcribe_audio()` (Whisper API).
3. Полученный текст идёт по пути UC-01.

**Особенность:** Если транскрипция вернула пустую строку или мусор («спасибо», «пока»), агент должен вернуть `status="ignored"`, а не пытаться записать пустую еду.

## UC-03: Запись через фото

**Актор:** Разработчик.

**Основной поток:**

1. Обёртка передаёт `agent.process(image_bytes=...)`.
2. Пакет вызывает Vision-LLM (GPT-4o / Gemini) с промптом, требующим вернуть JSON с `FoodItem[]` (название, граммовка, калории, БЖУ).
3. Далее — валидация и запись как в UC-01.

**Особенность:** Vision-LLM может вернуть несколько блюд на одной тарелке. Схема `NutritionEntry` должна поддерживать список `items`.

## UC-04: Смешанный ввод (текст + фото)

**Актор:** Разработчик.

**Основной поток:**

1. Обёртка передаёт `agent.process(text="Это мой обед", image_bytes=...)`.
2. Пакет отправляет в LLM оба входа. Текст используется как контекст («обед» → `meal_type="lunch"`), фото — как источник данных о еде.

**Зачем:** Пользователь может уточнить, что это за приём пищи, или добавить детали, которые не видны на фото («без масла»).

---

## UC-05: Мульти-Sink запись (Google Fit + Local SQLite)

**Актор:** Разработчик.

**Предусловие:** В конфигурации указаны два Sink-а: `google_fit` и `local_sqlite`.

**Основной поток:**

1. Пакет успешно распарсил еду.
2. Вызывает `GoogleFitSink.write(entry)`. Если Google API вернул 401 (токен протух) — Sink логирует ошибку, но **не прерывает** цепочку.
3. Вызывает `LocalSQLiteSink.write(entry)` — запись сохраняется локально.
4. Возвращает `ProcessResult` со списком: `sinks_succeeded=["local_sqlite"]`, `sinks_failed=["google_fit"]`.

**Зачем:** Если Google Fit недоступен, данные не теряются. Пользователь (или фоновый процесс) может позже «дослать» их в Fit.

---

## UC-06: Обратная связь (dry-run / предпросмотр)

**Актор:** Разработчик.

**Основной поток:**

1. Обёртка вызывает `agent.process(..., dry_run=True)`.
2. Пакет выполняет весь анализ (STT, LLM), но **не вызывает** Sink-и.
3. Возвращает `ProcessResult` с распарсенными данными.

**Зачем:** Бот может показать пользователю: «Я понял так: котлета 150г, гречка 200г — 450 ккал. Записать?» и только после подтверждения вызвать запись.
